# qa-clipper 運用の教訓

## このファイルの書き方（ふりかえり記録テンプレート）

事後レビューの最終OKが出たら、完了報告の前に必ず以下を行う:

1. **整理**: セッション中にユーザーが行った指摘・修正指示・質問・確認を時系列で洗い出す
2. **分類の提案**: 各項目を次の3種に分類してユーザーに提示:
   - **ルール化**（SKILL.md の仕様・チェックリスト・トラブルシューティングに反映すべきもの）
   - **記録のみ**（このファイルに経緯として残すもの）
   - **今回限り**（この動画固有の事情で、記録不要のもの）
3. **確認**: 「この分類でルール化・記録してよいか」をユーザーに確認する（無断で SKILL.md を書き換えない）
4. **反映**: 承諾を得たものを反映する。**SKILL.md に仕様を足した場合は、qa_report.md の仕様準拠チェック項目も同時に追加する**（ドキュメントとチェックのセット更新）

追記フォーマット:

```markdown
## YYYY-MM-DD 対象動画名（または作業内容）

### 指摘・確認事項
| # | ユーザーの指摘・確認 | 原因 | 対応 | 扱い |
|---|---|---|---|---|
| 1 | 終わりに次のQAが含まれる | AIが「最後の質問」を見逃し | analysis.json手修正+クロスチェック実装 | ルール化済み |

### 一般化した教訓
- （あれば。1〜3行で）
```

同じ教訓が既にある場合は新規追加せず「再発 YYYY-MM-DD」を既存項目に添える。

## 2026-07-07 20260706コンサルタント養成講座Q&A収録.mp4（15分27秒、Q&A5件）

### 一般化した教訓

**切り出し境界の最終確認は文字起こしではなく音声波形で行う。**

文字起こし（Whisper/faster-whisper）の単語タイムスタンプは、話の切れ目の判断材料としては便利だが、実際の発声終了時刻より0.2〜0.5秒早く出る傾向がある。余白（padding）を付けていた頃はこのズレが吸収されて問題化しなかったが、余白なしで正確に切ろうとすると露呈する。境界を追い込むほど、最終確認は波形ベースに切り替える必要がある。

### やり直しになった経緯

### ① 前後3秒の余白付きで納品 → やり直し
- 当初の設計は「短すぎて修正できないより、長めにして後からYouTube Studioで削る」という前提だった
- ユーザー指摘: 「前後の余白3秒はいらない。話始め・話終わりピッタリで切るように」
- 対応: `extract_qa_clips` の padding デフォルトを 3.0 → 0.0 に変更

### ② 余白ゼロにしたら文の途中で切れるクリップが発覧 → やり直し
- Claudeの `a_end`（回答終了時刻）が、次の質問への言い直しや相槌（「はい」）の直前で止まっていた
- 具体例: 「高評価店舗選択」クリップが「ぜひ頑張って」で途切れ、「ください」が欠けていた
- 対応: `snap_answer_endings()` を追加。単語間のギャップが0.8秒未満なら同一発話とみなして a_end を延長する。ただし次のペアの q_start は超えない

### ③ 文字起こしベースの補正だけで納品 → まだ切れていた（波形確認を省略していたため）
- ユーザー指摘: 「全体的に終わり部分がまだ切れている」（②の修正後も再発）
- 原因調査で判明した事実:
  - **Whisperの単語終了タイムスタンプは実際の発声より0.2〜0.5秒早い**（この動画の5クリップ全てで確認）
  - この動画は平均音量が**-40dB**と小さく、固定閾値（-30dB）での無音検出（`silencedetect`）が全く反応しなかった
- 対応: `refine_endings_by_silence()` を追加
  - 音源の `mean_volume` を測定し、閾値を `mean_volume - 6dB` として自動算出（固定値をやめた）
  - a_end 付近から後方の無音区間を波形で探索し、無音開始+0.12秒（語尾の余韻マージン）を新しい a_end とする
  - 次のペアの q_start は超えない

### 確立した3段階の終端補正パイプライン

```
Claude解析(a_end の生値)
  → validate_qa_pairs      # 順序整列・時間超過クランプ・重複除外
  → snap_answer_endings    # 文字起こしベース: 0.8秒未満のギャップは同一発話とみなして延長
  → refine_endings_by_silence  # 波形ベース: 実際の無音位置+0.12秒に最終補正
```

いずれの段も「次のペアの q_start を超えない」を共通の安全装置として持つ。これにより余白ゼロでも次の質問への食い込みは起きない。

### 検証に使ったコマンド（次回のデバッグ用）

```bash
# 動画・音声全体の平均/最大音量を確認（閾値のあたりをつける）
ffmpeg -i audio.wav -af volumedetect -f null -

# 特定区間の無音検出（閾値は mean_volume - 6dB 目安）
ffmpeg -ss <開始> -to <終了> -i audio.wav -af silencedetect=noise=<N>dB:d=0.3 -f null - 2>&1 | grep silence

# a_end 前後の単語を文字起こしJSONから目視確認
python3 -c "
import json
words = json.load(open('transcript.json'))
a_end = 338.38
near = [w for w in words if a_end-5 <= w['end'] <= a_end+3]
print(''.join(w['word'] for w in near))
"
```

### 今後の応用時の注意

- Zoom録画やマイク環境によって平均音量が大きく変わる（-40dB程度になることもある）。固定の無音閾値は使わない
- 「話し終わりぴったり」を求められた場合、文字起こしベースの補正だけでは不十分。必ず波形ベースの補正（`refine_endings_by_silence`）まで通すこと
- 完了報告の前に、少なくとも1本は `silencedetect` で語尾を実際に確認してからユーザーに提示する（[SKILL.md](../SKILL.md) の完了時チェックリストに反映済み）

### 一般化した教訓（④⑤⑥）

- ④ **AIの境界検出は必ずルールベースの定型句検出と突き合わせる。** 「続いての質問」「◯つ目の質問」等、収録フォーマットに定型の前振りがある場合は特に有効。AI単体の検出に依存すると、明確な区切りでも見逃すことがある
- ⑤ **「生成完了」と「完成」は別物。** 健全性・境界・カバレッジ・仕様準拠の自動検証（`verify_clips` → `qa_report.md`）を通し、レポートをユーザーに提示して最終OKを得てから完成とする
- ⑥ **SKILL.mdに書いた約束は、qa_report.mdの仕様準拠チェックとして機械照合する。** ドキュメントの更新とチェック項目の更新は必ずセットで行う。片方だけ直すと実態とドキュメントがズレて次回また事故になる

### 実装上の注意（テスト時に判明）

- `verify_clips` の境界検査は高速化のため faster-whisper `tiny` モデルを使う。精度が粗く、定型句を誤認識して偽陽性（例:「質問」→「スモン」）を出すことがある。これは想定内の挙動で、⚠️は自動失格ではなく「目視確認のトリガー」として扱う
- `verify_clips` に渡す `qa_pairs` は必ず `validate_qa_pairs → snap_answer_endings → refine_endings_by_silence` を通した最終値にすること。`analysis.json` の生値をそのまま渡すと「終端3段補正の適用」チェックが（正しく）⚠️になる

### 一般化した教訓
- ファイル配置ルール自体は動画編集プロジェクト共通のメモリ（`feedback_video_pipeline_review.md`）に準拠。qa-clipper固有なのは「qa_report.mdが✅合格でないと最終配置を実行できない」というゲート条件（事後検証の仕組みと連動させた点）
- **合否判定に混ぜる項目は「実際に問題を意味するか」を毎回吟味する。** カバレッジ検査は「参考情報として提示する」設計意図だったのに、実装時に無自覚に合否カウントへ混ぜてしまい、実害のないケースでブロックが発生した。チェック項目を追加するときは「これは合否を左右すべきか、それとも人間の判断材料に留めるべきか」を毎回問うこと
- **機械チェックの警告と人間の最終確認は別レイヤーとして扱う。** 自動チェックが100%の精度を持つ前提を置かず、「確認した上でのバイパス」を正規の経路として用意しておくと、誤検知のたびに設計を壊さずに済む

### 「冒頭に質問マーカーが見当たらない」警告の切り分け方（トラブルシューティング知見）

この警告は3パターンで発生しうる:
1. **tinyモデルの誤読**（例:「質問」→「スモン」） — 検査用の高速・低精度モデル特有の誤認識
2. **本当の境界ズレ** — クリップが前の回答の途中から始まっている
3. **定型句を使わない質問** — 「◯つ目の質問です」のような前振りがなく、いきなり内容から始まる質問

切り分け方: `qa_list.md` 作成時に使った**large-v3の文字起こし**（`transcript.json`）で、該当クリップの冒頭付近の単語を確認する。large-v3側で正しく質問フレーズが認識されていれば1番（誤検知）と判断できる。2番・3番の可能性は、実際に該当箇所の文言を読んで判断する。
